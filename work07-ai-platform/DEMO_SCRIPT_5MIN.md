# 5–7 Minute Live Demo Script: Work 07 & N+1 Latency Elimination

Цей сценарій створено для запису відео на 5–7 хвилин або для демонстрації екрана під час технічної співбесіди на посаду **Senior AI Backend Engineer**.

---

## Підготовка перед початком (за 2 хвилини до дзвінка)

1. Увімкніть Docker Desktop.
2. Відкрийте термінал у `work07-ai-platform`:
   ```powershell
   .\make.ps1 build; .\make.ps1 up
   ```
3. Відкрийте браузер на двох вкладках:
   * **Jaeger UI:** [http://localhost:16687](http://localhost:16687)
   * **RAG API Health:** [http://localhost:8090/health](http://localhost:8090/health) (`indexed_docs: 206`)
4. Відкрийте файл з кодом у редакторі:
   * `work07-ai-platform/services/logistics/src/main/java/ua/agrichain/logistics/service/EquipmentSearchService.java`

### [1:00 – 2:30] Як я виявив проблему (Jaeger & N+1 антипатерн)
* **Що показувати на екрані:** Jaeger UI (`http://localhost:16687`), пошук сервісу `logistics`. Відкрийте трейс запиту з профілем `slow`.
* **Що сказати:**
  > «Під час навантажувального тестування ендпоінта `POST /api/v1/equipment-requests` ми помітили високу затримку p95 — майже 200 мілісекунд на локальному стенді.
  > Я відкрив розподілене трасування в Jaeger. Погляньте на цей каскад: замість одного звернення до сервісу знань, сервіс Logistics розбивав рядок запиту на окремі токени та послідовно викликав Python RAG API для кожного токена окремо, плюс додатковий виклик для повної фрази.
  > Це класичний розподілений антипатерн **N+1 HTTP calls**. Кожен виклик додає затримку мережі, серіалізацію JSON і накладні витрати на прогін черги запитів.»

### [2:30 – 3:45] Що саме було змінено в коді (Java → Python)
* **Що показувати на екрані:** `EquipmentSearchService.java` (порівняння методів `searchSlow` та `searchFast`).
* **Що сказати:**
  > «Я переробив інтеграційний контракт:
  > Замість циклу по токенах ми реалізували єдиний батчевий гібридний виклик `searchFast()`.
  > У Python-сервісі ми використовуємо Reciprocal Rank Fusion (RRF) безпосередньо в Elasticsearch: поєднуємо kNN dense-вектори (SentenceTransformers) і розріджений пошук BM25 в одному запиті.
  > Ми також додали resilience-політики: тайм-аути на рівні RestClient, структуровані DTO та збереження контрактної зворотної сумісності через HTTP-заголовки.»

### [3:45 – 5:15] Докази та живий бенчмарк (p95: 197 ms → 47 ms)
* **Що показувати на екрані:** Запуск бенчмарку в терміналі:
  ```powershell
  py -3.13 scripts/benchmark_latency.py
  ```
* **Що сказати:**
  > «Зараз я запускаю стандартизований бенчмарк на 25 ітерацій за однакових умов локального стенду.
  > Результати:
  > * Профіль `slow` (N+1): p50 становить **~172 мс**, p95 — **~196 мс**.
  > * Профіль `fast` (один hybrid-виклик): p50 падає до **~34 мс**, p95 — до **~47 мс**.
  > Це чисте **прискорення у 4.2–5 разів** (speedup 4.2x на p95 і більше 5x на p50).
  > Усі сирі таймінги автоматично записуються в `artifacts/latency_raw_samples.json` разом із хешем коміту для 100% аудиту результатів.»

### [5:15 – 6:15] Валідація якості пошуку (BM25 vs Hybrid)
* **Що показувати на екрані:** Запуск або звіт `make.ps1 eval-hard`:
  ```powershell
  .\make.ps1 eval-hard
  ```
* **Що сказати:**
  > «Швидкість не повинна погіршувати якість. Ми перевірили якість retrieval на складній вибірці парафраз і синонімів із Work 02 (`hard_retrieval.json`).
  > Тут видно, що на запитах із точними термінами BM25 працює бездоганно, але коли користувач формулює запит розмовно або з синонімами, RRF Dense-компонента витягує релевантні агро-документи, які BM25 втрачає.
  > Тобто скорочення латентності на 75% зберегло повну точність видачі знань.»
